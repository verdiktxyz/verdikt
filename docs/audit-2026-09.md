## H-1 — Un perdant peut annuler un résultat FINAL par un 3e challenge (High)

**Le bug.** `reResolve()` est borné par `MAX_RE_RESOLUTIONS = 2`, mais `challenge()`
ne vérifie **pas** ce compteur. Après deux re-résolutions, un participant peut
déposer un 3e challenge : le vault entre en `Challenged`, `reResolve` revert
définitivement (`TooManyReResolutions`) — même pour des arbitres honnêtes — et la
seule sortie est la soupape de deadline : `cancel()`. Résultat : **les claims des
gagnants sont effacés, les sponsors remboursés, et le griefer récupère son bond**
(le `cancel` le lui rend).

**Impact.** Toute l'économie anti-griefing s'effondre au round 3 : un bond de
0,5 USDC — *rendu à l'attaquant* — détruit un résultat final de n'importe quelle
taille. Un perdant rationnel le fera systématiquement. PoC :
`test_F1_thirdChallengeForcesCancellation` (le sponsor récupère 100, le gagnant 0,
le griefer son bond).

**Correction** (dans `challenge()`, après le check de fenêtre) :

```solidity
function challenge() external payable inState(State.ResultProposed) {
    if (block.timestamp >= windowEndsAt) revert WindowClosed();
    // A result that can no longer be re-resolved is FINAL — unchallengeable.
    if (reResolutionCount >= MAX_RE_RESOLUTIONS) revert TooManyReResolutions();
    ...
```

Sémantique après fix : deux re-résolutions maximum, puis le résultat courant est
définitif et la fenêtre ne sert plus qu'au `finalize`. À documenter dans le README
(« after two re-resolutions, the standing result is final »).

## M-1 — Le bond d'un challenge infondé est orphelin après un clear (Medium)

**Le bug.** Challenge infondé → le bond est **fondu dans `claim[rank0]`**
(`claim += heldBond ; unclaimedTotal += heldBond`). Si un événement ultérieur
appelle `_clearClaims()` (2e challenge fondé, ou `cancel` depuis `Challenged`),
le clear remet `unclaimedTotal = 0` et efface les claims — **y compris le bond
fondu** — puis la ré-allocation ne redistribue que `prizePool`. Le bond reste dans
le solde du contrat **sans aucune écriture comptable** : verrouillé à jamais,
même une fois le vault `Closed`. L'invariant « not one wei created or lost » est
brisé. PoC : `test_F2_unfoundedBondOrphanedByClear` (solde final = 1 ether au
state Closed, toutes les entrées comptables à zéro).

**Impact.** Fonds bloqués (bornés : ≤ bond × re-résolutions), pas de vol — mais
c'est une violation d'invariant, et les invariants sont ton produit.

**Correction** (dans `reResolve()`, branche infondée) — router la compensation par
le canal `bondRefund`, qui **survit** aux clears et aux cancels par construction :

```solidity
if (founded) {
    bondRefund[challenger] += heldBond;
} else {
    // Griefing a winner pays the winner — via the pull channel that
    // survives _clearClaims() and cancellation.
    bondRefund[rankedWallets[0]] += heldBond;
}
```

(Supprimer les deux lignes `claim[...] += heldBond; unclaimedTotal += heldBond;`.)
Bonus de cohérence : si un 2e challenge fondé change le rang 1, l'ancien rang 1
garde la compensation du délai qu'il a réellement subi — plus juste que l'actuel.
L'UI affiche déjà `bondRefund` (bouton « Reclaim challenge bond ») : zéro
changement frontend, l'intitulé couvre les deux cas.

## Findings mineurs (Low)

- **L-1 · CEI dans `withdraw()`** : `state = Closed` est écrit *après* l'appel
  externe (flag slither reentrancy-eth). Aucun chemin exploitable trouvé (toutes
  les fonctions à état revert en `Withdrawable`, claims zérotés avant l'appel),
  mais l'ordre propre est gratuit : calculer `unclaimedTotal -= amount`, puis si
  `unclaimedTotal == 0` écrire `state = State.Closed` **avant** le `call`, et
  émettre les events après.
- **L-2 · `challengeBond = 0` autorisé** : ni le vault ni la factory n'imposent un
  bond minimum → challenges gratuits (2 re-résolutions forcées sans coût, et
  avant le fix H-1, l'attaque H-1 gratuite). Le paramètre est inspectable dans les
  Rules, donc c'est défendable — mais recommandé : `if (_challengeBond == 0)
  revert BadConfig();` ou au minimum un avertissement UI à la création.
- **L-3 · Griefing du dernier dépôt** : `deposit()` exige le complément *exact*
  (`Overfunded` sinon). Un attaquant peut front-runner le dépôt final d'un sponsor
  avec 1 wei pour le faire échouer, en boucle. Coût : son gas ; son wei est
  d'ailleurs récupérable seulement via cancel. Nuisance, pas vol — à connaître,
  fix optionnel (accepter et rembourser l'excédent compliquerait le modèle ;
  statu quo acceptable en beta).
- **L-4 · L'admin peut annuler un tournoi `Live`** avant la deadline (documenté
  dans le code : « before a result exists »). C'est un choix défendable — mais il
  contredit la copy UI/vidéo « nobody can touch it, not even the admin ». Deux
  options : retirer le droit admin de cancel en `Live` (le laisser en
  Created/Funded), ou corriger le message (« the admin can abort — never
  redirect »). À trancher *avant* le mainnet : c'est une promesse publique.

## Informationnel

- **I-1** : `snapshot()` n'expose ni `heldBond`, ni `reResolveDeadline`, ni
  `reResolutionCount` — l'UI de l'état Challenged les lira en appels séparés.
- **I-2** : le contrat n'utilise jamais `address(this).balance` dans sa logique →
  le force-feeding (selfdestruct/EIP-6780) est inoffensif. ✅
- **I-3** : factory sans bornes sur `name`/`rankBps.length` (auto-nuisance du
  créateur uniquement) ; `all()` non paginé grossit sans borne — `page()` existe,
  l'UI devra basculer à l'échelle.
- **I-4** : le reste du bruit slither (locals non-initialisées = idiome zéro,
  timestamps = par design, low-level calls = pull payments voulus) : écarté après
  revue.

## Ce qui tient — et tient bien

L'attestation est **solide** : ordre strictement croissant des signataires =
rejet des doublons sans storage, malléabilité ECDSA gérée par OZ v5, les 4
couches anti-replay sont réelles (domaine chainId+vault, tournamentId, hash du
classement, round), et le seuil M > N/2 est imposé au constructeur. Les trois
sorties d'argent sont en pull strict avec zérotage avant appel. `RankMath` +
`assert(allocated == prizePool)` verrouillent la comptabilité de l'allocation
(c'est d'ailleurs ce qui rend M-1 si visible). Le garde-fou podium, l'allowlist
de wallets, l'absence de tout chemin vers une adresse arbitraire : vérifiés.
La factory est sans owner et sans fonds — surface minimale. Les 29 tests + fuzz
couvrent bien le happy path et les gardes ; ce qui manquait, c'était les
**interactions entre challenges successifs** — exactement là où H-1 et M-1
vivaient.

## Procédure de sortie mainnet

1. Appliquer H-1 + M-1 (et L-1/L-2 recommandés) — ~10 lignes.
2. Garder `AuditPoC.t.sol` dans la suite en **mode régression** : après fix,
   inverser les assertions (le 3e challenge doit revert ; le solde final doit
   être 0). Objectif : 31+/31 verts.
3. Trancher L-4 (droit d'annulation admin en Live) et aligner la copy.
4. Redéployer la factory (testnet pour vérif, puis mainnet — wallet neuf).
5. Plafonds beta affichés (≤ 250 USDC/pool) tant qu'aucun audit externe /
   bounty n'a eu lieu — cet audit interne réduit le risque, il ne le supprime
   pas : un second cerveau externe reste l'étape suivante (Immunefi bounty
   modeste en Phase 3, comme prévu dans la roadmap).
